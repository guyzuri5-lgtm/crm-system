# CRM — WhatsApp + Gmail + Next.js/Supabase

מימוש של האפיון "מערכת CRM" (וואטסאפ ⟷ קוד ⟷ Gmail, בלי Make). ר' [הקמה מאפס](#הקמה-מאפס) לפני שמנסים להריץ אותו על אמת.

> **הערה על הערוץ:** האפיון המקורי דיבר על ManyChat, והמערכת נבנתה מולו. הוא הוחלף בסופו של דבר ב-**WhatsApp Cloud API הרשמי של Meta** — ר' [ערוץ הוואטסאפ](#ערוץ-הוואטסאפ) להסבר מלא על מה השתנה ולמה, כולל תחנת הביניים ב-Green API.

## ארכיטקטורה

```
וואטסאפ  ──webhook (Meta)──────────────▶  /api/webhooks/whatsapp  ┐
                                                                     │
וואטסאפ  ◀────────── Cloud API ─────────────  automation-engine ───┤── Supabase (Postgres)
                                                                     │
תיבת Gmail ◀──────────  Gmail API ──────────  automation-engine ───┘
                                                     ▲
                                          /api/cron/check-rules (יומי)
                                                     ▲
                                              דשבורד (Next.js, Supabase Auth)
```

הקוד הוא ה"מוח" בשני הכיוונים — הוא מחליט מתי ולמי לשלוח, בלי מתווכים. ר' [האפיון המקורי](#) שסופק לפרויקט לפרטים המלאים; המסמך הזה מתמקד במה שבפועל נבנה ובמה שעדיין צריך להשלים.

## סטאק

Next.js 16 (App Router, Turbopack) · Postgres + Auth דרך Supabase · Vercel (hosting + cron) · Gmail API (OAuth2) · WhatsApp Cloud API. כמו באפיון המקורי סעיף 2, למעט ערוץ הוואטסאפ שהוחלף.

**הערה על Next.js 16:** הגרסה הזו החליפה `middleware.ts` ב-`proxy.ts` (אותה מנגנון, שם אחר) ושינויים נוספים לא-שגרתיים. אם ממשיכים לפתח כאן עם עוזר AI — יש `AGENTS.md` בשורש שמפנה למסמכי הגרסה הנכונה תחת `node_modules/next/dist/docs/`; שווה לוודא שהוא עדיין שם ורלוונטי לפני שינויים גדולים.

## מה כבר בנוי

- **סכימת DB מלאה** (`supabase/migrations/0001_init.sql`) — כל 5 הטבלאות מהאפיון + 2 תוספות (ר' למטה), הרשאות RLS, טריגר שמוסיף `team_members` אוטומטית כשמזמינים משתמש חדש ב-Supabase Auth.
- **כל ה-endpoints מסעיף 4**: `/api/webhooks/whatsapp`, `/api/cron/check-rules`, `/api/contacts` (+ `/[id]`), `/api/send/email`, `/api/send/whatsapp`.
- **מנוע הכללים** (`src/lib/automation-engine.ts`) — status_change + time_since_no_reply, כולל בדיקת חלון 24 השעות ובחירה בין הודעה חופשית לפלואו-תבנית.
- **דשבורד מלא**: התחברות (Supabase Auth), רשימת אנשי קשר עם סינון, כרטיס איש קשר עם לוג אינטראקציות ועדכון סטטוס/הערות, ניהול כללי אוטומציה, ניהול תבניות הודעה.
- **סטטוסים דינמיים** (`0003_statuses.sql`) — הסטטוסים הם שורות בטבלת `contact_statuses`, לא `enum`, ולכן ניתנים להוספה/עריכה/מחיקה/סידור מעמוד `/statuses`. שינוי שם מתגלגל לכל אנשי הקשר דרך `on update cascade`, ומחיקה מחייבת לבחור סטטוס להעביר אליו את מי שמשויך. הסטטוס הראשון בסדר התצוגה הוא ברירת המחדל לליד חדש (טריגר `contacts_fill_default_status`, לא `default` על העמודה — כדי שמחיקת הסטטוס הזה לא תשבור כל `insert` מה-webhook).
- **שינוי סטטוס מתוך שורת הטבלה** — התגית ב-`/contacts` היא כפתור שפותח רשימה (`src/components/status-picker.tsx`), בלי להיכנס לכרטיס איש הקשר.
- **ייבוא מאקסל/CSV** — `/contacts` ← "ייבוא מקובץ". זיהוי כותרות אוטומטי (עברית ואנגלית), דה-דופליקציה לפי טלפון/מייל מול הקיים ובתוך הקובץ עצמו, ודוח שורה-שורה על מה שדולג. קורא `.xlsx` ו-CSV בלי תלות חיצונית (`src/lib/spreadsheet.ts`) — חבילת `xlsx` ב-npm נטושה, ו-.xlsx הוא ZIP+XML שאפשר לפרק עם `zlib` המובנה של Node. **ייבוא לא מפעיל כללי אוטומציה** בכוונה, כדי שהעלאת רשימה לא תשלח מאות הודעות.
- **מערכת זימון פגישות** (`0005_booking.sql`) — קישור ציבורי בסגנון Calendly (`/book/<slug>`), זמינות שמוצלבת מול יומן גוגל בזמן אמת, יצירת אירוע עם Google Meet והזמנה ללקוח, פתיחת כרטיס לקוח אוטומטית ומייל אישור. ראו את הסעיף המלא בסוף המסמך.
- **`npm run build` עובר נקי** (TypeScript + ESLint + Next build) — נבדק בפועל, כולל הרצת dev server ובדיקת מספר endpoints ידנית (ראו קוד/היסטוריית העבודה אם רוצים לשחזר את הבדיקות).

## שינויים והוספות לעומת האפיון המקורי

כמה החלטות שהתקבלו תוך כדי בנייה, שלא היו מפורשות באפיון:

1. **`contacts.whatsapp_id` (שדה חדש)** — ה-`wa_id` של Meta: המספר בפורמט בינלאומי בלי `+` (`972501234567`). נשמר ולא מחושב מחדש בכל פעם, כי מה שהתקבל בפועל מ-Meta אמין יותר מהמרה של מספר שמישהו הקליד.
2. **`automation_rule_runs` (טבלה חדשה)** — בלי זיכרון של "הכלל הזה כבר רץ על איש הקשר הזה", ה-cron היומי לכללי `time_since_no_reply` היה שולח את אותה הודעה **כל יום מחדש** לכל מי שחצה את הסף. הטבלה הזו מונעת את זה.
3. **`interactions.external_id` (שדה חדש)** — ה-`wamid` של Meta. Meta חוזרת על כל webhook שלא נענה ב-200, ובלי מזהה ייחודי ניסיון חוזר היה מייצר שורה כפולה ביומן איש הקשר. הוא גם מה שמחבר הודעה יוצאת לעדכון המסירה שמגיע אחריה. אינדקס יחיד *חלקי* (רק על שורות שאינן NULL) מאפשר לשורות פנימיות — הערה ידנית, פגישה, מייל יוצא — להישאר בלי מזהה.
4. **RLS + service role, לא RLS בלבד** — הדשבורד/ה-API מדברים עם Supabase דרך מפתח ה-service role (עוקף RLS), כי "כולם באותה הרשאה" זה בדיוק המודל שלא צריך RLS-per-user. מדיניות ה-RLS עדיין קיימת בטבלאות כקו הגנה שני, למקרה שמפתח ה-anon ייחשף אי-פעם לצד לקוח.
5. **הדשבורד קורא מ-Supabase ישירות, לא דרך `/api/contacts`** — ה-endpoint קיים (לפי דרישת סעיף 4), אבל דפי הדשבורד עצמם קוראים ישירות דרך ה-Server Client של Supabase (הדפוס המקובל ב-App Router) כדי לא לעשות קריאת HTTP מיותרת לעצמם.
6. **דה-דופליקציה על ה-webhook הנכנס** — לפי `idMessage`, ר' פריט 3.
7. **חלון 24 השעות הוא הכלל שקובע הכול** — ר' [ערוץ הוואטסאפ](#ערוץ-הוואטסאפ).

## הקמה מאפס

### 1. Supabase

1. צרו פרויקט חדש ב-[supabase.com](https://supabase.com).
2. SQL Editor ← הריצו את המיגרציות שבתיקיית `supabase/migrations/` **לפי הסדר** (`0001_init.sql`, `0002_quiz.sql`, `0003_statuses.sql`, ...) — כל אחת בנפרד (או `supabase link` + `supabase db push` אם עובדים עם ה-CLI). כל מיגרציה מתחילה בבלוק reset, אז אפשר להריץ אותה שוב אם משהו נכשל באמצע.
3. Project Settings → API — העתיקו `URL`, `anon public key`, ו-`service_role secret` ל-`.env.local` (ר' `.env.example`).
4. **הוספת אנשי צוות** (אין הרשמה עצמאית במערכת, בכוונה): Authentication → Users → Add user, מלאו אימייל+סיסמה, סמנו Auto Confirm. הטריגר ב-migration יוסיף אותם אוטומטית ל-`team_members`. *(שיפור עתידי אפשרי: מסך "שכחתי סיסמה"/הזמנה עצמאית — לא נבנה ב-v1 הזה.)*
5. כשמחברים לפרויקט אמיתי, כדאי לייצר את הטיפוסים מהסכימה החיה במקום `src/lib/supabase/database.types.ts` הידני:
   ```bash
   npx supabase gen types typescript --project-id <ref> > src/lib/supabase/database.types.ts
   ```
   (ואז לוודא שהוא עדיין תואם למה שהקוד מצפה לו — הוא נשען על זה שלכל טבלה יש `Relationships: []`, ר' הערה בקובץ.)

### 2. וואטסאפ (Meta Cloud API)

זה השלב הארוך בהקמה, ורובו המתנה ולא עבודה. **אימות העסק מול Meta עלול לקחת ימים** ולדרוש מסמכים (ח.פ./עוסק מורשה) — שווה להתחיל ממנו.

1. **Meta Business Account** ב-[business.facebook.com](https://business.facebook.com), ואימות העסק (Business Settings → Security Center).
2. **אפליקציה** ב-[developers.facebook.com](https://developers.facebook.com) מסוג Business, והוספת המוצר **WhatsApp**.
3. **הוספת המספר** ואימותו. Meta שולחת SMS או מתקשרת; מספר וירטואלי (Zadarma וכדומה) עובד, ובלבד שהוא קולט SMS או שיחה.

   ⚠️ **המספר לא יכול להיות רשום במקביל בוואטסאפ רגיל.** אם רשמת אותו באפליקציה — צריך למחוק שם את החשבון קודם.

4. **הזנת המפתחות**: `npm run setup:whatsapp`. הסקריפט מבקש שלושה ערכים, כותב אותם ל-`.env.local`, מייצר `WHATSAPP_WEBHOOK_VERIFY_TOKEN` אקראי, ומיד שולף מ-Meta את מצב המספר כדי לוודא שהם תקפים. ההקלדה מוסתרת ואינה נשמרת בהיסטוריית הטרמינל.

   | הערך | איפה מוצאים |
   |---|---|
   | `WHATSAPP_PHONE_NUMBER_ID` | WhatsApp → API Setup. **מזהה, לא מספר הטלפון** |
   | `WHATSAPP_ACCESS_TOKEN` | ראו האזהרה למטה |
   | `WHATSAPP_APP_SECRET` | App Settings → Basic |

   ⚠️ **הטוקן שמוצג בדף API Setup פג אחרי 24 שעות** וטוב רק לבדיקה ראשונה. לפרודקשן: Business Settings → System Users → משתמש מערכת עם הרשאת `whatsapp_business_messaging` → Generate token → **ללא תפוגה**.
5. **חיבור ה-webhook**: WhatsApp → Configuration → Callback URL:

   | שדה | ערך |
   |---|---|
   | Callback URL | `https://<הדומיין-שלכם>/api/webhooks/whatsapp` |
   | Verify token | אותו ערך כמו `WHATSAPP_WEBHOOK_VERIFY_TOKEN` |
   | Subscribe to | `messages` |

   Meta קוראת מיד ב-GET ומצפה לקבל בחזרה את `hub.challenge`. הראוט עושה את זה לבד; אם האימות נכשל, כמעט תמיד ה-Verify token לא זהה בשני הצדדים.

6. **תבניות**: WhatsApp Manager → Message Templates. צרו לפחות תבנית תזכורת אחת בקטגוריית **Utility** (לא Marketing — היא יקרה בהרבה ועוברת אישור קפדני יותר). אחרי האישור, הזינו את שמה המדויק ואת שפתה בעמוד **תבניות הודעה** בדשבורד.

### 3. Gmail (Google Cloud OAuth2)

1. [Google Cloud Console](https://console.cloud.google.com) → פרויקט חדש (או קיים) → **APIs & Services → Library** → הפעילו את **Gmail API**.
2. **APIs & Services → OAuth consent screen** — סוג External (חשבון Gmail רגיל, לא Workspace, אין אפשרות Internal). כל עוד המסך במצב **Testing**: רק "Test users" שתוסיפו יכולים להרשות גישה — תוסיפו שם את חשבון ה-Gmail השולח. **חשוב:** במצב Testing, ה-refresh token פג אחרי כ-7 ימים — אם לא רוצים לחדש אותו ידנית כל שבוע, יהיה צריך "לפרסם" (Publish) את המסך; בגלל שההיקף `gmail.send` נחשב רגיש, פרסום מלא עשוי לדרוש תהליך אימות של גוגל. שיקלול הפשרה הזו הוא בעצם סעיף 7 המקורי ("האם צריך OAuth consent screen מאומת") — עדיין החלטה פתוחה.
3. **Credentials → Create Credentials → OAuth client ID → Web application** → `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.
4. קבלת `GOOGLE_REFRESH_TOKEN` (חד-פעמי) — יש סקריפט שעושה את כל התהליך:
   ```bash
   npm run auth:google
   ```
   הוא מבקש את שני ה-scopes יחד — `gmail.send` **וגם** `calendar` — ומחזיר טוקן אחד שמשרת גם את שליחת המייל וגם את יומן הפגישות. לפני ההרצה צריך להוסיף `http://localhost:53682` ל-**Authorized redirect URIs** של ה-OAuth Client ב-Google Cloud.

   > **אם כבר יש לכם טוקן ישן** שהופק עם `gmail.send` בלבד — הוא ימשיך לשלוח מיילים אבל יחזיר 403 מול היומן. הריצו את הסקריפט והחליפו אותו.
5. מלאו גם `GMAIL_SENDER_EMAIL` (חשבון השולח בפועל) ו-`GMAIL_SENDER_NAME` (השם שמוצג לנמענים).
6. מכסת שליחה: חשבון Gmail רגיל מוגבל בערך ל-500 מיילים ביום, Workspace בערך 2,000 — שווה לוודא מול [התיעוד העדכני](https://support.google.com/a/answer/166852) אם זה עדיין רלוונטי, אבל בנפח שדיברתם עליו (50–200 לידים/חודש) יש המון מרווח.

### 4. יומן גוגל (למערכת זימון הפגישות)

1. **APIs & Services → Library** → הפעילו את **Google Calendar API** (בנוסף ל-Gmail API).
2. הריצו `npm run auth:google` והחליפו את `GOOGLE_REFRESH_TOKEN` בערך שהוא מחזיר (ראו סעיף 3).
3. הריצו את `supabase/migrations/0005_booking.sql` ב-SQL editor של Supabase.

   > **סדר המיגרציות חשוב.** 0005 מגדיר מפתח זר אל `contact_statuses`, שנוצרת ב-`0003_statuses.sql`. אם 0002–0004 עוד לא הורצו על הפרויקט — הריצו אותן לפי הסדר קודם, אחרת 0005 ייכשל.
4. בדשבורד → **פגישות** → **שעות זמינות והגדרות**: הגדירו אזור זמן, את היומן שאליו נכתבות הפגישות (`primary` = היומן הראשי), ואת שעות העבודה.

אם היומן לא מחובר, המערכת עדיין עובדת — אבל היא מציעה שעות לפי הזמינות שהוגדרה בדשבורד בלבד, בלי לדעת מה תפוס ביומן. הדשבורד מציג על כך אזהרה בולטת.

### 5. דומיין + Vercel

1. `vercel deploy` (או חיבור ה-repo ב-Vercel dashboard).
2. Project Settings → Environment Variables — הזינו את כל מה שב-`.env.example`.
3. `vercel.json` כבר מגדיר cron יומי ל-`/api/cron/check-rules` בשעה 06:00 UTC (≈ 8–9 בבוקר בישראל, תלוי שעון קיץ) — שנו את ה-schedule אם רוצים שעה אחרת. ברגע שמגדירים `CRON_SECRET` כמשתנה סביבה, Vercel שולח אותו אוטומטית כ-`Authorization: Bearer <CRON_SECRET>` — אין צורך בקוד נוסף.
4. הדומיין הסופי (זמני מ-Vercel כמו `your-app.vercel.app`, או דומיין קסטום) הוא מה שהולך ב-Callback URL של ה-webhook ב-Meta.

## פיתוח מקומי

```bash
npm install          # כבר רץ; מריצים שוב רק אם עדכנתם package.json
cp .env.example .env.local   # ואז למלא ערכים אמיתיים
npm run dev
```

`npm run build` ו-`npx eslint .` רצים נקי גם בלי חיבור לחשבונות אמיתיים (עם `.env.local` שמכיל ולו ערכים placeholder בפורמט הנכון) — שימושי כבדיקת "לא שברתי כלום" תוך כדי פיתוח.

## מה עוד לא בנוי

- ערוץ הוואטסאפ עבר ל-Cloud API הרשמי. Gmail ו-Supabase מחוברים ועובדים. מה שעדיין לא נבדק end-to-end מסומן בסעיפים הרלוונטיים.
- קריאת תגובות/אימיילים נכנסים מ-Gmail (האפיון ביקש שליחה בלבד).
- טסטים אוטומטיים.

## ערוץ הוואטסאפ

הערוץ הוחלף פעמיים. שתי ההחלפות היו נכונות, וכל אחת נבעה מעובדה שלא הייתה ידועה קודם — שווה לדעת מה הן, כדי לא לחזור אליהן.

```
ManyChat  ──►  Green API  ──►  Meta Cloud API
   │              │                  │
   │              │                  └─ הערוץ הרשמי. בלי מכשיר, בלי סיכון חסימה.
   │              └─ דרש טלפון פיזי שהחשבון חי עליו. מת על מספר וירטואלי.
   └─ מתווך מעל ה-API הרשמי, עם מגבלות משלו על גבי אלה של Meta.
```

### למה לא ManyChat

ManyChat ישב *מעל* WhatsApp Business API ומכר גישה אליו — כלומר כל המגבלות של Meta, ועוד שכבה משלו:

| | ManyChat | Cloud API ישיר |
|---|---|---|
| חלון 24 שעות | יש | יש — חוק של Meta |
| תבניות מאושרות | יש | יש — חוק של Meta |
| בניית "פלואו" ידני לכל תבנית | חובה | לא קיים |
| `flow_ns` במקום שם תבנית | חובה | שולחים לפי שם |
| שליחת טקסט חופשי | דרך שדה מותאם + פלואו, כי `sendContent` שבור לוואטסאפ | קריאת HTTP אחת |
| שליחה למי שלא כתב קודם | בלתי אפשרי (`subscriber_id` נוצר רק אחרי הודעה נכנסת) | לפי מספר טלפון |
| תוכנית PRO ל-webhook יוצא | חובה | לא קיים |
| עלות | מנוי חודשי קבוע | לפי שימוש |

**מה שחזר עם Cloud API הוא שני חוקים של Meta. מה שלא חזר הוא כל מה שבאמת כאב.**

### למה לא Green API

Green API מתחבר לחשבון WhatsApp אמיתי דרך פרוטוקול WhatsApp Web. אין בו חלון 24 שעות ואין תבניות — שליחה היא קריאה אחת, בכל זמן. זה היה נראה כמו הפתרון הטוב ביותר, עד ששתי עובדות הכריעו:

1. **הוא דורש מכשיר פיזי.** מהתיעוד שלהם: *"חייבת להיות אפליקציית WhatsApp מותקנת בטלפון"* ו*"הטלפון חייב להיות תמיד טעון ומחובר לאינטרנט"*. המספר העסקי כאן הוא מספר וירטואלי בלי מכשיר, וזה חוסם את המסלול לגמרי.
2. **המספר חשוף לחסימה.** זה ערוץ לא רשמי, ושליחה יזומה בהיקף היא בדיוק הדפוס שוואטסאפ חוסם עליו. כשכל העסק תלוי במספר אחד, זה סיכון שקשה להצדיק.

הקוד שלו נמחק, אבל הוא בהיסטוריית ה-git אם אי פעם יהיה מכשיר ויעדיפו שיחה חופשית על פני בטיחות.

### הכלל שקובע הכול היום

בכל רגע, כל איש קשר נמצא באחד משני מצבים:

| מצב | מתי | מה מותר | עלות |
|---|---|---|---|
| 🟢 חלון פתוח | הלקוח כתב ב-24 השעות האחרונות | כל טקסט חופשי | חינם |
| 🔴 חלון סגור | לא כתב, או שמעולם לא כתב | רק תבנית מאושרת | מחויב |

זה נאכף בשלושה מקומות, וכולם עוברים דרך `sendMessageToContact` (`src/lib/send.ts`) שמחליט לבד לפי `contacts.last_incoming_message_at`:

- **כרטיס הלקוח** מציג את המצב הנוכחי ומאפשר רק את מה שחוקי בו.
- **כלל אוטומציה** של מעקב פונה מעצם טבעו למי שלא ענה — כלומר כמעט תמיד מחוץ לחלון. לכן **לכל כלל כזה חייבת להיות תבנית מאושרת**, אחרת השליחה נכשלת במפורש. זו התנהגות מכוונת: עדיף כישלון גלוי מהודעה שלא יוצאת בשקט.
- **`POST /api/send/whatsapp`** מקבל `template_id` ו/או `body`, ונותן לאותה לוגיקה להחליט.

### מה קורה לנתונים הקיימים

שתי המיגרציות שומרות על ההיסטוריה ולא מוחקות אותה:

- **`0009`** — `interactions` מסוג `manychat_in`/`manychat_out` מומרו ל-`whatsapp_in`/`whatsapp_out` (ה-enum הוחלף כולו; פוסטגרס לא מאפשר להסיר ערך מ-enum).
- **`0011`** — `whatsapp_chat_id` שונה ל-`whatsapp_id`, והסיומת `@c.us` הוסרה מהערכים כדי שאנשי קשר שנקלטו דרך Green API ימשיכו להיות מזוהים. מזהי קבוצות רוקנו — Cloud API אינו עובד עם קבוצות.

מספרים שנשמרו כ-`+972501234567` בימי ManyChat ממשיכים להימצא: החיפוש עובר דרך `phoneVariants`, שמשווה גם מול הצורה המקומית `0501234567`.

## בלמים על השליחה האוטומטית

**דשבורד → וואטסאפ.** חלים על הקרון היומי בלבד; שליחה ידנית מכרטיס לקוח לא נחסמת, אבל כן נספרת בתקרה.

המנגנון נבנה במקור נגד **חסימה** של המספר, כשהערוץ היה Green API. ב-Cloud API אין סיכון כזה — זה הערוץ המאושר — ולכן ההשהיות בין הודעות ירדו (`0011`). מה שנשאר, ומשמעותו התהפכה:

| בלם | ברירת מחדל | מה הוא עושה |
|---|---|---|
| תקרה יומית | 40 | כבר לא מגן על המספר אלא על **הכיס**. כל תבנית שנמסרת מחויבת, ולולאה שהשתבשה היא חשבונית |
| מתג עצירה | כבוי | עוצר את הקרון מיד, בלי deploy ובלי לגעת בכללי האוטומציה |
| תקציב זמן ריצה | נגזר מ-`maxDuration` | שהפונקציה לא תמות באמצע ותשאיר חצי רשימה בלי הודעה |

השלישי הוא לא נימוס אלא נכונות. פונקציה ב-Vercel נקטעת **בכוח** כשנגמר לה הזמן — אין `onShutdown` ואין הזדמנות לסיים. בלי לעצור מרצון לפני כן, ההודעה שבאמצע שליחה נעלמת בלי שיירשם עליה כלום.

### למה עצירה באמצע היא בטוחה

`automation_rule_runs` נכתבת **רק אחרי שליחה מוצלחת**. מי שלא הספיק יימצא שוב בריצה הבאה, ומי שכן קיבל לא ייבחר שוב. אין כאן "מצב" לשמור בין ריצות ואין סיכון לשליחה כפולה — הרזומביליות היא תוצאה של מבנה שכבר היה שם, לא מנגנון חדש.

### איכות המספר

Meta נותנת לכל מספר דירוג (`quality_rating`) שנגזר מתלונות וחסימות של נמענים, והוא מוצג בדף **וואטסאפ** בדשבורד:

| דירוג | משמעות |
|---|---|
| 🟢 GREEN | אין תלונות חריגות |
| 🟡 YELLOW | הצטברו תלונות — כדאי לצמצם פניות יזומות ולבדוק את נוסח התבניות |
| 🔴 RED | Meta עלולה להגביל את המספר |

זו ההתראה המוקדמת היחידה לפני הגבלה בפועל, והיא לא מגיעה לשום מקום אחר אלא אם בודקים. ירידה ל-YELLOW היא הרגע להשהות ולבדוק למי נשלח.

### הגדלת הקצב

הקרון רץ פעם ביום ומוגבל בזמן ריצה. מי שלא נשלח אליו נשלח בריצה הבאה.

**תקציב הזמן אינו נגזר מ-`maxDuration`.** `maxDuration` הוא בקשה ולא הבטחה — ב-Hobby הוא נחתך בשקט ל-60 שניות, ותקציב שנגזר מ-300 היה גורם ללולאה להאמין שיש לה פי חמישה זמן ממה שיש. התוצאה: הפונקציה נקטעת בכוח באמצע שליחה, בלי `onShutdown` ובלי הזדמנות לרשום מה יצא — בדיוק הכשל שהמנגנון נועד למנוע.

לכן התקציב מגיע מ-`CRON_TIME_BUDGET_SECONDS`, שברירת המחדל שלו **45** — בטוחה ב-Hobby:

| תוכנית | חלון פונקציה | להגדיר | הודעות בריצה |
|---|---|---|---|
| Hobby | 60 שניות | ברירת מחדל | ~15 |
| Pro | 300 שניות | `CRON_TIME_BUDGET_SECONDS=280` | ~90 (בפועל נחסם בתקרה היומית) |

ואפשר גם לפזר על כמה הרצות ביום — מה שגם פורס את ההודעות על פני היום:

```json
"crons": [
  { "path": "/api/cron/check-rules", "schedule": "0 9 * * *" },
  { "path": "/api/cron/check-rules", "schedule": "0 15 * * *" }
]
```

**דורש Vercel Pro.** ב-Hobby הוספת הרצה שנייה *תפיל את ה-deploy* — התוכנית מגבילה לקרון יומי אחד, וביטוי תכוף יותר נדחה עם `Hobby accounts are limited to daily cron jobs`. זו הסיבה ש-`vercel.json` נשאר עם הרצה אחת.

## שאלון הצ'אקרות → CRM

השאלון (`../index.html`) שולח כל מילוי ל-`POST /api/webhooks/quiz`, ומשם הוא נשמר
בטבלה `quiz_submissions` ומתחבר ל-`contacts` הקיימת.

### הפעלה

1. הריצו את `supabase/migrations/0002_quiz.sql` ב-SQL editor.
   `0004_quiz_results_email.sql` **אינו חובה** — ראו "מייל הדוח המלא" למטה.
2. ב-`.env.local` הוסיפו `QUIZ_ALLOWED_ORIGIN` (הדומיין של השאלון), ואם רוצים גם
   `QUIZ_WEBHOOK_SECRET`.
3. ב-`index.html` הגדירו:
   ```js
   WEBHOOK_URL: "https://<הדומיין>/api/webhooks/quiz",
   WEBHOOK_SECRET: "",   // רק אם הגדרתם QUIZ_WEBHOOK_SECRET
   ```

### שלוש רשומות, שורה אחת

| מתי | `kind` | מה קורה |
|---|---|---|
| בסיום השאלון | `anonymous` | נשמרת התוצאה וכל 21 התשובות. **לא** נוצר איש קשר. |
| אחרי הטופס | `lead` | נוצר או מתעדכן `contact`, והמילוי מקושר אליו. |
| בלחיצה על קביעת פגישה | `booking_click` | מסומן `booking_clicked_at`. |

כולן חולקות `session_id` שנוצר בדפדפן בתחילת המילוי, וממוזגות לשורה אחת.
ה-`kind` רק עולה בדרגה — מי שכבר יצא לקבוע פגישה לא חוזר להיות אנונימי.

### התאמה לאיש קשר

לפי טלפון (מנורמל ל-`05XXXXXXXX`, השדה ייחודי בסכימה) ואז לפי אימייל. איש קשר
חדש נוצר עם `source = "שאלון צ'אקרות"` ותגיות `שאלון צ'אקרות` + `חסומה: <שם המרכז>`.
**ה-`status` של איש קשר קיים לא נדרס** — זה שדה שהצוות מנהל ידנית.

כל מעבר שלב נרשם ב-`interactions` עם הסוג `quiz_submitted`, כך שהוא מופיע ביומן
של איש הקשר לצד וואטסאפ ומיילים.

### מייל הדוח המלא

מי שממלא את הטופס מקבל במייל את "הדוח המלא על שבע הצ'אקרות" — בדיוק מה שהטופס
מבטיח: המפה האנרגטית, מדד האיזון, ולכל אחד משבעת המרכזים אבחון והצעד הראשון.

השליחה עוברת ב-`sendMessageToContact` (Gmail API), ולכן היא נרשמת ביומן איש
הקשר כ-`email_out` בדיוק כמו כל מייל אחר. היא רצה ב-`after()` — מחוץ למסלול
הקריטי, כדי שתקלה ב-Gmail לא תפיל את קליטת הליד.

**חד-פעמיות — שני מסלולים.** המסלול הראשי הוא העמודה
`quiz_submissions.results_email_sent_at`: עדכון מותנה (`... is null`) תופס את
הזכות לשלוח לפני השליחה, ואם השליחה נכשלת החותמת מתנקה בחזרה והכישלון נרשם
ביומן איש הקשר. זה אטומי — שתי בקשות מקבילות, רק אחת שולחת.

כל עוד `0004_quiz_results_email.sql` לא רץ, הקוד נופל למסלול גיבוי שנשען על
היומן: אם כבר נרשם `email_out` עם הקידומת `[דוח שאלון צ'אקרות]` לאיש הקשר הזה
בעשר הדקות האחרונות — לא שולחים שוב. זה מכסה רענון דף, ניסיון חוזר של הדפדפן
ולחיצה על "קביעת פגישה" מיד אחרי הטופס, בלי לחסום מילוי חוזר אמיתי כעבור זמן.
הוא **אינו** אטומי, ולכן בשתי שליחות בו-זמניות ממש ייתכן מייל כפול.

כלומר: הפיצ'ר עובד גם בלי המיגרציה, והרצת 0004 משדרגת את החד-פעמיות מ"טובה
מספיק" ל"הרמטית". קליטת הליד עצמה לא תלויה בעמודה בשום מצב.

**התוכן:** כל הטקסטים נשאבים מ-`../index.html` אל
`src/lib/quiz-copy.generated.ts`. אחרי כל עריכת תוכן בשאלון הריצו:

```bash
npm run sync:quiz-copy
```

הם מכוון **לא** מגיעים ב-payload: endpoint ציבורי שמקבל טקסט חופשי ושולח אותו
במייל לכתובת כלשהי הוא ממסר ספאם בשם גיא. מאותה סיבה גם הסטטוס של כל מרכז
מחושב מחדש בשרת מהציונים, ולא נלקח מ-`payload.statuses`.

`QUIZ_CALENDLY_URL` קובע את קישור ה-CTA במייל (ברירת מחדל: זה שבשאלון).

### צפייה בתוצאות

בדף איש הקשר (`/contacts/[id]`) מופיע בלוק עם התוצאה המלאה: גרף הקו של שבעת
המרכזים, דמות המדיטציה עם המרכז החסום מסומן, שבעת הציונים, וכל ההיגדים עם
התשובה שנבחרה. אם אדם מילא יותר מפעם אחת — כל המילויים מוצגים, החדש קודם.

### אבטחה

ה-endpoint ציבורי מעצם טבעו: הוא נקרא מדפדפן של גולש אנונימי, ולכן כל מפתח
שנשתול ב-HTML גלוי בקוד המקור. ההגנה היא ולידציה קפדנית ב-`src/lib/quiz.ts`
(zod, עם תקרות על כל שדה) והעובדה שהוא כותב בלבד ולא מחזיר מידע.
`QUIZ_WEBHOOK_SECRET` מרתיע סורקים אוטומטיים — הוא אינו אבטחה אמיתית.
אם הדף ייחשף לתנועה גבוהה, כדאי להוסיף rate limiting.

## מערכת זימון פגישות

קישור ציבורי בסגנון Calendly. הלקוח בוחר יום ושעה, ממלא פרטים, והמערכת סוגרת את כל המעגל: אירוע ביומן, Google Meet, כרטיס לקוח ב-CRM, ומייל אישור.

### הקישור

לכל **סוג פגישה** יש כתובת משלו:

```
https://<הדומיין>/book/<slug>
```

הקישור פתוח לחלוטין — הלקוח לא נרשם ולא מתחבר. הנתיב `/book` רשום ב-`PUBLIC_PATHS` שב-`src/proxy.ts`; בלי זה הוא היה מופנה למסך התחברות.

### מה קורה כשנסגרת פגישה

לפי הסדר, ובסדר הזה בכוונה:

1. **אימות מחדש של השעה** — הזמינות מחושבת מחדש בשרת. השעה שהדפדפן שלח לא נחשבת אמינה: היא נראתה לפני דקה, והיומן יכול היה להתמלא בינתיים.
2. **שמירת הפגישה ב-DB** — לפני היומן. אילוץ `exclude using gist` על `bookings` הוא הבורר האטומי היחיד בין שני אנשים שלחצו על אותה שעה; אילו יצרנו קודם את האירוע ביומן, המפסיד במרוץ היה משאיר אירוע יתום.
3. **אירוע ביומן** — עם `sendUpdates: "all"` (הלקוח מקבל הזמנה מגוגל) ועם `conferenceDataVersion: 1` שיוצר קישור Meet. **כשל כאן לא מבטל את הפגישה** — השעה כבר שמורה, והדשבורד מסמן אותה "לא סונכרן ליומן" כדי שאפשר יהיה לתקן ידנית.
4. **כרטיס לקוח** — חיפוש לפי טלפון ואז לפי מייל; מי שכבר קיים מתעדכן בלי לדרוס שדות שכבר מלאים, ומי שלא — נפתח לו כרטיס חדש עם `source = "זימון פגישה"`.
5. **רישום ביומן איש הקשר** (`interactions`) ועדכון סטטוס, אם הוגדר כזה לסוג הפגישה.
6. **מייל אישור** מהג'ימייל שלך, עם קישור ה-Meet וקישור ביטול.

### איך מחושבת הזמינות

הצלבה של חמישה מקורות (`src/lib/booking/slots.ts`):

| מקור | מה הוא עושה |
|---|---|
| שעות שבועיות | החלונות שבהם אפשר להיפגש. אפשר כמה חלונות ליום, ואפשר שעות מיוחדות לסוג פגישה מסוים |
| חסימות ידניות | חלונות חד־פעמיים שנחסמים — חופשה, נסיעה, יום עמוס |
| יומן גוגל | האירועים בזמן אמת, על היומן הראשי ועל יומנים נוספים לבחירה. אירועי יום־שלם, אירועים שסומנו "פנוי" והזמנות שנדחו **אינם** חוסמים — ראו למטה |
| פגישות שנקבעו | גיבוי ל-freeBusy, כדי שהמערכת תעבוד נכון גם לפני שהיומן חובר |
| הגדרות סוג הפגישה | משך, זמן מגן לפני/אחרי, התראה מוקדמת מינימלית, וכמה ימי לוח קדימה נפתח היומן |

**זמן מגן (buffer)** לא נכתב כאירוע ביומן — הוא רק מונע הצעת שעה שנצמדת לפגישה קיימת. כך "רבע שעה לנשום בין פגישות" לא דורש אירועי דמה ביומן.

**כשל מול גוגל מחזיר 503, לא רשימה ריקה.** "אין שעות פנויות" ו"לא הצלחנו לבדוק" נראים זהים ללקוח, והראשון שקרי — עדיף להציג הודעת שגיאה מאשר להזמין מישהו לשעה תפוסה.

#### אירועי יום־שלם ביומן (תוקן)

הזמינות נשלפת מגוגל דרך `events.list` ולא דרך `freeBusy`. ההבדל אינו טכני:

`freeBusy` מחזיר טווחי "תפוס" מוכנים אבל בלי שום מידע *על* האירוע, ולכן אירוע יום־שלם חוזר ממנו כבלוק תפוס של 24 שעות — בדיוק כמו פגישה. יום הולדת, חג, תזכורת או סימון "יום מרוכז" מחקו **יום שלם של פגישות אפשריות** מהקישור הציבורי, בלי שום סימן ללקוח או למארח. אירוע יום־שלם שנמשך שבוע מחק שבוע.

`events.list` מחזיר את השדות שמאפשרים להבחין, ולכן שלושת אלה כבר לא חוסמים:

| מה | למה זה לא חוסם |
|---|---|
| אירוע יום־שלם | ברוב המקרים הוא סימון ולא פגישה. ניתן להדליק חסימה ב**פגישות ← הגדרות** למי שמסמן חופשות ככה |
| אירוע שסומן "הצג אותי כפנוי" (`transparency`) | המארח כבר הצהיר במפורש שהוא לא תפוס בו |
| הזמנה שנדחתה | פגישה שלא הולכים אליה לא תופסת את היומן |

פגישות רגילות עם שעות חוסמות תמיד, בלי קשר להגדרה. יומן משותף שנחשף בהרשאת "פנוי/תפוס בלבד" מחזיר 403 על `events.list`, והקוד נופל בשבילו בחזרה ל-`freeBusy` — הוא ייספר כתפוס גם על אירועי יום־שלם, וזה מכוון: עדיף לחסום יום מיותר מאשר לקבוע פגישה כפולה.

#### חלון הימים קדימה

`max_days_ahead` נמדד ב**ימי לוח, כולל היום**: `2` = היום ומחר במלואם, `7` = השבוע הקרוב. הוא חל *מעל* שעות הזמינות ולא במקומן — יום שאין בו שעות פתוחות יישאר סגור גם אם הוא בתוך החלון.

הספירה הזו החליפה חישוב מתגלגל של `now + N × 24h`, שחתך את היום האחרון בדיוק בשעה הנוכחית: הלקוח ראה חצי יום פתוח וחצי סגור בלי סיבה נראית לעין, והגבול זז עם כל רענון של הדף.

### אזורי זמן

שעות הזמינות נשמרות כ**דקות מחצות** ולא כטיפוס `time` או כ-timestamp. הן שעות *קיר*: 9:00 בירושלים הוא `06:00Z` בקיץ ו-`07:00Z` בחורף, וההמרה חייבת לקרות לכל תאריך בנפרד. `src/lib/booking/timezone.ts` עושה זאת דרך `Intl` בשני מעברים, בלי ספריית תאריכים ובלי טבלת מעברי שעון קיץ לתחזק.

הלקוח רואה את השעות **באזור הזמן של עצמו**, עם ציון מפורש מתחת לרשימה.

### ניהול

הכל תחת **פגישות** בדשבורד:

- **סוגי פגישות** — שם, כתובת קישור, משך, רזולוציית השעות המוצעות, זמני מגן, התראה מוקדמת, חלון ימים קדימה, מיקום (Meet / טלפון / פרונטלי), ולאיזה סטטוס להעביר את הליד. כיבוי סוג פגישה מנטרל את הקישור בלי למחוק היסטוריה.
- **שעות זמינות והגדרות** — שעות שבועיות, חסימות ידניות, אזור זמן, היומן שאליו נכתבות הפגישות, יומנים נוספים לבדיקת תפוסה, והאם אירוע יום־שלם חוסם.
- **כרטיס המארח** — תמונה, שם ותפקיד שמוצגים ללקוח בראש דף ההזמנה. התמונה עולה לבאקט `booking-assets` ב-Supabase Storage (נוצר ב-`0008`), עד 2MB, JPG/PNG/WEBP. הבאקט ציבורי לקריאה כי הדף שמציג אותה רץ בלי משתמש מחובר; ההעלאה עצמה עוברת דרך service role בלבד.

### העיצוב של דף ההזמנה

הדף נצבע בצבע שנבחר לסוג הפגישה. הצבע מוזרק כארבעה משתני CSS (`--accent`, `--accent-strong`, `--accent-soft`, `--accent-muted`) על עוטף הדף, ויורד בירושה לכל מה שמתחתיו — כולל `BookingFlow`, שהוא רכיב לקוח ולא מקבל את הצבע כ-prop. זה לא סגנון שרירותי אלא אילוץ אמיתי: Tailwind v4 מייצר CSS רק למחלקות שהוא רואה כתובות במלואן בקוד המקור, ולכן `bg-${color}-50` שנבנה בזמן ריצה פשוט לא היה מייצר שום סגנון. הפלטה עצמה ב-`src/lib/booking/accent.ts`.

פגישת **Google Meet** מסומנת במפורש — לוגו, כיתוב, והסבר שהקישור יישלח במייל — בשלושת השלבים: בחירת המועד, מילוי הפרטים, ומסך האישור. "איפה הפגישה" הוא הדבר שהכי שואלים עליו *אחרי* קביעה, והמקום לענות עליו הוא לפניה.

### ביטול

מייל האישור כולל קישור ביטול עם טוקן של 24 בייטים אקראיים (`bookings.cancel_token`) — ולא ה-`id`, כדי שניחוש מזהים לא יאפשר ביטול פגישות של אחרים. ביטול מוחק את האירוע מהיומן (גוגל שולח הודעת ביטול), משחרר את השעה, ונרשם ביומן איש הקשר. אפשר לבטל גם מהדשבורד.

### מה עוד לא נבדק

שליפת הזמינות **נבדקה** מול חשבון אמיתי (אוגוסט 2026) — כולל התקלה של אירועי יום־שלם שתוארה למעלה, וכולל אימות שפגישות אמיתיות עם שעות אכן מסתירות את השעות שלהן.

מה שעדיין לא נבדק מול חשבון אמיתי הוא צד ה**כתיבה**: יצירת האירוע עם קישור Meet, ההזמנה שהלקוח מקבל מגוגל, ומחיקת האירוע בביטול.

לוגיקת אזורי הזמן **כן** נבדקה — כולל מעברי שעון הקיץ של 2026 (27 במרץ ו-25 באוקטובר) והשעה שלא קיימת ביום המעבר.
